# 09-07 — Agent 的「测试预言家」—— 让 AI 在 bug 出现前就堵上门

> **一句话：别等 bug 炸了你再修，让 Agent 在写代码时就帮你把测试布好，bug 刚冒头就被按死。**

---

## 💀 这个场景是不是太熟悉了

你刚写完一个功能，自信满满地提交，结果：

- 测试覆盖率从 78% 掉到 52% 🫠
- 线上报了一个边界 case，你完全没考虑到
- 重构的时候改崩了三个地方，但测试全绿（因为压根没测那些路径）
- Code Review 时同事问："这个函数的测试呢？" 你："……马上补"

**停。** 测试不是写完代码后的「家庭作业」，它是 Agent 能帮你提前做好的「护城河」。

---

## 🎯 技巧一：TDD 反向操作——让 Agent 先写测试，你再写实现

传统 TDD 是先写测试再写代码，但很多人嫌麻烦。现在有 Agent 了，你可以让 AI 帮你把最烦的部分——**写测试骨架**——瞬间搞定。

### 实操流程

**Step 1：描述需求，让 Agent 生成测试用例**

```
我要实现一个函数 `validateEmail(email)`，需要满足：
- 标准邮箱格式通过
- 缺少 @ 符号报错
- 域名部分无效报错
- 空字符串报错
- 超长邮箱（>254 字符）报错

请帮我把这些场景的单元测试骨架写出来，用 Jest 语法。
不要写实现，只写测试。
```

Agent 会给你一个完整的 `describe` + `it` 结构，包含所有边界 case。

**Step 2：你写实现，跑测试**

写完实现后跑一遍，红的变绿，成就感拉满。

**Step 3：让 Agent 补你漏掉的 case**

```
这是我写的实现：
@validateEmail.ts

测试都过了，但帮我看看还有没有漏掉的边界 case，
特别是那些我没想到的「邪门」输入。
```

Agent 可能会告诉你：
> "你漏了 `email` 为 `null` 的情况，还有带多个 @ 符号的（`a@b@c.com`），以及 Unicode 域名……"

**这就是人和 AI 的互补——你想主线，AI 想边界。**

## 🕵️ 技巧二：给祖传代码「补体检」—— 让 Agent 批量生成测试

legacy 代码没测试？别慌，让 Agent 帮你「考古 + 补测」同步进行。

### 投喂模板

```
这个文件没有测试，帮我补一个基础测试文件：

@src/utils/formatter.ts

要求：
1. 覆盖所有导出函数的「主流程」
2. 每个函数至少 1 个正常 case + 1 个边界 case
3. 如果有明显会抛异常的路径，也测一下
4. 用 [你的测试框架] 语法

先列出你计划覆盖的测试点，确认后我再让你写完整代码。
```

**为什么先让 Agent 列计划？**

因为 Agent 可能会漏掉某些函数，或者误解某个函数的用途。你先看一眼它打算测什么，对齐预期，再让它写完整代码——**省掉返工**。

### 高阶玩法：覆盖率定向补齐

```
这是当前的测试覆盖率报告（只贴了 <80% 的文件）：

[贴 coverage 报告]

帮我给这些文件补测试，优先覆盖：
1. 当前 uncovered 的行
2. 条件分支（if/else/switch）
3. 错误处理路径

不需要 100%，把明显漏的补上就行。
```

Agent 能读懂覆盖率报告，精准定位「哪里没测到」。

## 🛠️ 各工具实操

### Claude Code

```
# 场景 1：新功能先写测试

我要实现一个函数，功能是 [描述清楚]。
请帮我写完整的 Jest 测试用例，包括：
- 正常输入
- 所有我能想到的边界情况  
- 异常输入

写完后告诉我："你觉得还有哪些 case 是我应该考虑但没提到的？"

---

# 场景 2：给老代码补测试

@src/legacy-module.ts

这个文件没有测试。请帮我：
1. 先总结一下这个文件里每个函数是干嘛的
2. 然后为每个函数写基础测试（主流程 + 1 个边界）
3. 测试文件放在 __tests__/legacy-module.test.ts
```

Claude Code 可以直接 `@` 引用文件，然后让测试写到正确位置。

### Cursor

Cursor 的 **Composer** 特别适合「测试 + 实现」双开：

1. 在 Composer 里输入："给这个函数写测试" + 选中代码
2. Cursor 会自动在侧边生成测试文件
3. 你可以在 Composer 里迭代："再加一个边界 case"、"这个 mock 不对"

**Cursor 的 Yolo 模式延伸**：
```
这个模块目前零测试。帮我：
1. 建一个测试文件
2. 覆盖核心函数的主流程
3. 如果跑不通，帮我修 mock 和依赖

直接改，改完告诉我覆盖率变化。
```

### Kimi Code

Kimi Code 的长上下文优势：**一次性把整个模块 + 测试需求丢进去**。

```
这是 utils/date.ts 的完整代码（可能比较长）：

[粘贴代码]

请帮我写对应的单元测试，要求：
- 用 Vitest
- 覆盖所有导出函数
- 包含时区相关的边界 case（如果有）
- mock Date.now() 来测时间相关逻辑
```

Kimi 不怕代码长，能把整个模块的测试一次性生成完整。

## 🧠 为什么这招有效？

| 没有 Agent | 有 Agent |
|---|---|
| 写测试 = 额外的「家庭作业」，能拖就拖 | Agent 10 秒生成骨架，你只需要填实现 |
| 边界 case 全靠经验，新手根本想不到 | Agent 会系统性枚举边界：null、undefined、空串、超长、特殊字符…… |
| 老代码不敢重构，因为没有测试兜底 | Agent 帮你补测试，重构有安全网 |
| 覆盖率报告看了头疼，不知道补哪 | Agent 直接定向补齐 uncovered 行 |

**核心原因**：写测试的「机械劳动」部分（造数据、写 assert、铺 case）Agent 比你快 100 倍，而「判断测什么、验证对不对」这种判断力，你比 Agent 准。分工合作，效率翻倍。

## 💡 进阶玩法

### 玩法 1：「测试即文档」

让 Agent 把测试写成「可读性优先」的风格：

```
帮我把这些测试改写成 "Given-When-Then" 格式，
让没看过代码的人也能通过测试名看懂这个函数的行为。
```

好的测试名就是最好的文档：
```javascript
it('given an invalid email without @, when validating, then throws FormatError')
```

### 玩法 2：让 Agent 当「破坏王」

```
我写了这些测试，帮我看看够不够「狠」。

请扮演一个「故意找茬」的 QA，看看能不能想到：
1. 什么输入会让我的实现崩溃？
2. 什么并发/时序问题我可能没考虑？
3. 什么资源泄漏或性能陷阱？
```

Agent 的「找茬模式」经常能挖出你想不到的坑。

### 玩法 3：测试驱动重构

```
这是当前实现和它的测试：

@old-implementation.ts
@old-implementation.test.ts

我想重构这个实现（目标：[描述目标，比如简化逻辑、抽离函数]），
但要求：测试一行不改，全部继续通过。

请帮我做重构，如果测试需要调整，先问我。
```

**这就是测试的核心价值——它是重构的「安全带」。**
