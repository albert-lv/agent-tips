# Agent 的「重构提案」模式——改代码前先让 AI 写一份 RFC

> **一句话总结**：别让 AI 直接动手重构，先让它写一份「最小 RFC」，列出改什么、不改什么、风险在哪、怎么验证。你审完再执行，返工率降 80%。

---

## 💬 场景：你是不是经常这样？

你对着一段祖传代码叹气：

> "这坨逻辑太乱了，我想重构一下……"

然后你打开 Claude Code / Kimi Code / Cursor，说：

> "帮我重构这段代码，让它更 clean。"

AI 唰唰唰改完，你一看——

- 改了 12 个文件，diff 比你命还长 🫠
- 把本来能跑的 edge case 改崩了
- 引入了新的抽象层，但只用到一次
- 你花了 20 分钟 review，最后选择 `/undo`

**问题不是 AI 不会重构，是你没给 AI 画边界。**

---

## 🎯 技巧：先让 AI 写「重构提案」

核心思想很简单——**像人类工程师一样，先评审方案，再动手实现。**

### 三步走

#### 第一步：投喂上下文 + 提出诉求

```
我想重构 [文件/模块名]，目标是 [具体目标，比如"提取公共逻辑到独立函数"]。

请先不要改代码，而是给我一份"重构提案"，包含：
1. 当前问题诊断（哪里乱、为什么需要改）
2. 重构方案（具体怎么改，改哪些文件）
3. **明确不改什么**（哪些代码保持原样，为什么）
4. 风险点（可能破坏什么，怎么防）
5. 验证步骤（改完后我怎么确认没坏）
```

#### 第二步：评审 + 调整

AI 给完提案后，你可以：

- "方案 2 不错，但第 3 步会影响 XX 模块，改成……"
- "风险点 2 我没考虑到，加一条回滚策略"
- "不改的范围太宽了，其实 Y 文件也可以一起改"

**这一步把「AI 的即兴发挥」变成「双方对齐的方案」。**

#### 第三步：执行

确认方案后，再让 AI 动手：

```
按我们确认的方案执行重构。每一步改完告诉我改了什么，我确认后再继续。
```

或者如果你用的是 Claude Code 的 `!` 模式 / Cursor Yolo，也可以：

```
按上述方案执行，遇到不确定的地方停下来问我。
```

## 🛠️ 各工具实操

### Claude Code

```
/compact  # 先压缩上下文，把空间留给重构分析

[粘贴上述 prompt]

# AI 给完提案后，你可以用 @ 精准引用某段代码讨论细节
"@src/utils.ts 的第 45-60 行，这部分你计划怎么处理？"
```

### Kimi Code

```
# Kimi Code 的长上下文很适合让 AI 先看完整文件再出方案
"先看完这三个文件，给我一份重构提案，不要动手改。"

# 确认方案后
"按上面的方案执行，每次只改一个函数，改完汇报。"
```

### Cursor

```
# 把提案要求写进 .cursorrules，变成默认行为
"Before large refactoring, always write a mini-RFC first."

# 或者在 Composer/Chat 里用
"先出方案，我 approve 再执行。"
```

---

## 🧠 为什么这招有效？

| 痛点 | 传统做法 | 重构提案模式 |
|---|---|---|
| 改得太多 | AI 自由发挥，改 12 个文件 | 方案里明确「改哪 3 个文件」 |
| 改崩 edge case | AI 不知道哪些逻辑不能碰 | 「不改什么」清单直接画红线 |
|  Review 很痛苦 |  diff 巨大，看不懂意图 | 先看方案，diff 只是执行细节 |
| 来回 undo | 改完发现方向错了 | 方向错了在提案阶段就发现 |

**本质是把 AI 从「工匠」变成「顾问」——先出方案，你拍板，它执行。**

## 💡 进阶玩法

### 玩法 1：对比方案

让 AI 出 2-3 个不同力度的方案：

```
给我三个选项：
A. 保守方案：只改命名和格式，不动结构
B. 中等方案：提取公共函数，减少重复
C. 激进方案：重写核心逻辑，引入新抽象

每个方案列出改动范围、风险、预计耗时。
```

### 玩法 2：让 AI 自己当「反对者」

```
假设你是代码审查员，给这个重构提案挑刺。
有哪些理由可以反对这个方案？
```

AI 会自己列出风险，你把风险补进提案里。

### 玩法 3：沉淀为模板

把常用 prompt 存到你的 `CLAUDE.md` / `.cursorrules` 里：

```markdown
## 重构规范
任何涉及 3 个以上文件的重构，必须先输出重构提案，包含：
- 问题诊断
- 改动范围（明确改什么、不改什么）
- 风险点
- 验证步骤
- 用户 approve 后方可执行
```

## 📝 今天记住这个

| 场景 | 操作 |
|---|---|
| 想重构但怕改崩 | 先让 AI 写「重构提案」 |
| AI 提案范围太大 | 明确说「不改什么」 |
| AI 给了方案但你不确定 | 让 AI 自己当反对者挑刺 |
| 经常做同类重构 | 把 prompt 写进项目规范文件 |

> **核心心法**：AI 不是越快越好，是越对齐越好。花 3 分钟对齐方案，省 30 分钟 review + undo。
