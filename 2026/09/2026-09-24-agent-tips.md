# 09-24 — Agent 的「交叉评审」—— 让 AI 当自己的质检员，bug 无所遁形

## 🪞 一个反直觉的事实

用 AI 写代码的人，大概率也用 AI 审代码——但用的是**同一个 Agent、同一个模型、同一段上下文**。

这就像让作者自己校对自己的稿子：不是不细心，是**大脑会自动跳过自己写的东西**。模型也一样——它对自己刚生成的代码有种"父爱滤镜"，看你夸过的方案会自动补全合理性。

2026 年的解法很简单：**换个脑子来挑刺。**

## 🧠 技巧一：Claude Code —— 养一个「毒舌审查员」子代理

上周刚说完子代理能隔离上下文（09-18）和配便宜模型（09-23），今天把两个技能合起来用：

在 `.claude/agents/reviewer.md` 里定义一个专门唱反调的分身：

```markdown
---
name: reviewer
description: 毒舌代码审查员，专门挑刺
model: opus  # 审查是硬仗，值得花
---

你是一个严苛的代码审查员。你的唯一任务是找出问题，不是夸奖。
审查任何代码时，你必须：
1. 找出至少 3 个潜在问题（bug、边界条件、性能陷阱、安全隐患）
2. 对每一行「看起来没问题」的代码追问：如果输入是空的？如果是并发？如果数据量 ×1000？
3. 明确说出「这段代码在什么情况下会爆炸」
4. 禁止说「整体很好」这类废话
```

然后写完代码，一句话召唤：

```
/review 用 reviewer 子代理审查刚才的改动，只报告问题
```

关键设计：**审查员用 Opus，写代码用 Sonnet**。生成的时候快、便宜；挑刺的时候狠、准、不惜算力。这比「写完自己看一遍」的命中率高出不止一个量级。

> 💡 进阶玩法：**对抗式审查**。先让主 Agent 写代码，然后对审查员说「这段代码是另一个工程师写的，他水平一般，请狠狠挑刺」。摘掉「自己人」滤镜，毒舌值直接拉满。

## 🔄 技巧二：跨工具交叉验证 —— 用 Kimi Code 审 Claude Code 写的代码

如果两个模型有相同的盲区（比如都偏爱某种模式），内部互审效果会打折。真正的交叉验证是**跨模型**：

- **Claude Code 写完 → 丢给 Kimi Code 审**：`kimi 帮我审查这个实现的正确性和边界处理，重点关注并发安全和资源泄漏`
- **Kimi Code 写完 → 丢给 Claude Code 审**：尤其是涉及复杂类型体操、Rust 生命周期这种「推理链越长越香」的场景

两个模型的训练数据不同、思维链不同、踩过的坑不同——**一个模型的盲区，往往正好是另一个模型的舒适区**。

> ⚠️ 注意：交叉验证不是互相推诿。如果两个 Agent 意见冲突，以「谁能给出可复现的反例」为准。能跑起来的反对意见才是有效反对。

## ⚡ 技巧三：Cursor —— Composer 写完，Chat 来审

Cursor 里没有子代理，但有一样好用的东西：**让 Composer 生成，切到 Chat 模式审查**。

原因是 Composer 和 Chat 的上下文组织方式不同——Composer 满脑子都是「我要把这堆改动串起来」，Chat 从零看 diff 反而更客观。配合这个 prompt 模板效果拔群：

```
我刚完成了这组改动。请假装你是一个不熟悉这个项目的资深工程师，
第一次看到这个 diff。请找出：
1. 哪些改动会让你困惑？（命名、结构、魔法数字）
2. 哪些改动可能引入 bug？（边界条件、错误处理、竞态）
3. 如果这是生产代码，你最担心什么？
```

「第一次看到这个 diff」是魔法咒语——它强制 Chat 忘掉生成时的上下文，用陌生眼光看代码。

## 📝 今天记住这个

| 场景 | 解法 |
|---|---|
| 写完代码自己审不出毛病 | `.claude/agents/reviewer.md` 养个毒舌子代理，强制找出 3 个问题 |
| 省预算但想要高质量审查 | 写代码用 Sonnet/快模型，审查员切 Opus/旗舰模型 |
| 同一个模型审自己 = 左手打右手 | Claude Code 写完丢 Kimi Code 审，跨模型盲区互补 |
| Cursor 里没有子代理 | Composer 生成 → Chat 审查，「第一次看到这个 diff」咒语 |
| 两个 AI 意见打架 | 谁能给出可复现的反例听谁的 |

一句话总结：**写代码用一个人，审代码换一个人——这个道理对 AI 同样成立。** 🎯
