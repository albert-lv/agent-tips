# 09-06 — Agent 的「报错翻译官」—— 把鬼畜报错变成人话

> **一句话：报错不是天书，是让 Agent 帮你翻译成人话、找出根因、甚至修好它的信号弹。**

---

## 💀 这个场景是不是太熟悉了

你正在愉快 coding，突然终端一片红：

```
TypeError: Cannot read property 'map' of undefined
    at /src/components/List.tsx:42:17
    at Array.filter (<anonymous>)
    at processTicksAndRejections (internal/process/task_queues.js:97:5)
```

你的大脑：

1. **第一阶段（ denial ）**："刷新一下就好了"
2. **第二阶段（ anger ）**："这代码刚才还能跑！"
3. **第三阶段（ bargaining ）**："我把 `?.` 加上试试……不对，加在哪？"
4. **第四阶段（ depression ）**：打开 12 个 Stack Overflow 标签页，没一个完全匹配
5. **第五阶段（ acceptance ）**：开始一行行 `console.log`

**停。** 把报错丢给 Agent，30 秒给你人话版诊断，2 分钟给你修复方案。

---

## 🎯 技巧一：报错的「正确投喂姿势」

别只丢一行报错。Agent 不是神，它也需要上下文。

### ❌ 低效问法

```
这个报错什么意思？
TypeError: Cannot read property 'map' of undefined
```

Agent："可能是 `data` 为 undefined 了，你检查一下。"

你："……我也知道可能是 undefined 啊，关键是哪来的？"

### ✅ 高效问法（三段式）

```
我遇到了这个报错：

[完整报错堆栈，复制粘贴]

出错的代码上下文：
[贴上报错位置前后 10-20 行代码]

我的预期行为是：
[描述你期望发生什么]

请帮我：
1. 用人话解释这个报错的根因（不是表面原因）
2. 给出具体的修复代码
3. 告诉我怎么防止再次发生
```

**为什么这样更有效？**

| 信息 | Agent 能做什么 |
|---|---|
| 只给报错 | "可能是 undefined" |
| 报错 + 代码 | "第 42 行的 `data` 在第 38 行可能为 undefined" |
| 报错 + 代码 + 预期 | "你的 API 返回格式变了，建议加个类型守卫 + fallback" |

## 🕵️ 技巧二：让 Agent 当「侦探」，不是「翻译器」

报错是**症状**，不是**病因**。让 Agent 帮你挖到根因。

### 追问模板（连环三问）

**第一问（现象）**：
```
这个报错表面上是什么意思？
```

**第二问（追踪）**：
```
根据代码上下文，这个 undefined 最可能是从哪传进来的？
帮我追踪数据流：从 API 返回 → 组件 props → 报错位置
```

**第三问（根治）**：
```
除了修复这个报错，我的数据流里还有哪些地方有同样的风险？
给我一个防御性编程的建议。
```

**Agent 可能会告诉你**：

> "表面上是 `List.tsx:42` 的 `data.map()` 炸了，但根因是上游 `fetchUserData()` 在接口超时时返回了 `undefined` 而不是空数组。你在 3 个组件里都直接用了 `.map()`，建议统一加 `|| []` 或者上 TypeScript 严格模式。"

**这才是你要的——不是修一行，是修一类。**

## 🛠️ 各工具实操

### Claude Code

```
# 在 terminal 里看到报错，直接选中复制，然后：

我遇到了这个报错，帮我分析根因和修复方案：
[粘贴完整报错]

报错位置的代码：
@src/components/List.tsx:35-50

# Claude 会读取文件 + 分析报错 + 给修复代码
# 确认后可以直接让它 apply
```

**高阶玩法**：让 Claude 批量检查同类风险
```
基于刚才的分析，帮我扫描整个项目里还有哪些地方有类似的 "直接 .map() 不做空值检查" 的风险。
列出文件和行号。
```

### Cursor

Cursor 的优势是**报错即问**：

1. 在 Terminal 看到报错 → 选中报错文本
2. 右键 → "Add to Chat"（或 `Ctrl+L` / `Cmd+L`）
3. 自动带上报错 + 相关代码文件
4. 直接问："这个报错的根因是什么？怎么修？"

**Cursor Composer 的 Yolo 模式**：
```
这个报错帮我修一下，同时检查同类型的防御性代码缺失。
直接改，改完告诉我改了哪些文件。
```

### Kimi Code

Kimi Code 的长上下文适合处理**超长日志**：

```
我在跑测试时遇到了报错，这是完整的测试输出日志（可能很长，你慢慢看）：

[粘贴几百行日志]

请帮我：
1. 找到真正的报错信息（忽略 warning 和无关输出）
2. 解释根因
3. 给出修复方案
```

Kimi 的长上下文优势：不怕日志长，能从海量输出里定位真正的错误。

## 🧠 为什么这招有效？

| 你自己排查 | Agent 帮你排查 |
|---|---|
| 眼睛在报错里找关键词 | 同时分析报错 + 代码 + 数据流 |
| 凭经验猜可能原因 | 基于完整上下文做因果推理 |
| 修完一个，下一个同样炸 | 能识别「同类风险」批量预防 |
| Stack Overflow 搜 20 分钟 | 30 秒给诊断，2 分钟给修复 |

**核心原因**：报错信息是「结果」，代码是「过程」，Agent 能同时看两者，而人类往往只盯着报错本身发呆。

## 💡 进阶玩法

### 玩法 1：建立「报错词典」

如果你经常遇到同类报错，让 Agent 帮你建一个内部速查表：

```
我们项目经常遇到 "Cannot read property X of undefined" 这类报错。
帮我写一个「防御性编程 Checklist」，包含：
1. 常见触发场景
2. 修复模式（?.、|| default、类型守卫）
3. 预防建议（TypeScript strict、API 响应校验）
```

存到项目的 `docs/error-playbook.md`，新人来了直接看。

### 玩法 2：让 Agent 写「自动防护」

修完一个报错后：

```
刚才这个 bug 是因为 API 返回格式不符合预期。
帮我写一个数据校验函数，放在 API 层统一处理，
确保不符合预期的数据在源头就被拦截，给出清晰的错误信息。
```

从「修 bug」升级到「防 bug」。

### 玩法 3：报错预演（适合 Code Review）

```
这段代码有哪些地方可能在运行时抛异常？
给我列出一个「风险清单」，按严重程度排序。
```

让 Agent 在代码合并前就帮你找雷。
