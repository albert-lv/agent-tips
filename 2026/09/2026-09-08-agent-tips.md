# 09-08 — Agent 的「Spike 快刀」—— 10 分钟验证一个想法，别在纠结中内耗

> **一句话：纠结「这个方案行不行」的时候，让 Agent 10 分钟搭个能跑的原型，用事实打败纠结。**

---

## 🫠 这个场景是不是太熟悉了

你坐在电脑前，脑子里有两个声音在打架：

**声音 A**："我觉得用 WebSocket 做实时推送更合适，SSE 太简单了不够用。"

**声音 B**："但 WebSocket 要维护连接状态、心跳、重连逻辑，SSE 虽然简单但够用了啊……"

**声音 A**："万一后面要做双向通信呢？"

**声音 B**："现在又不是双向通信，你过度设计了。"

**你**：打开 8 个浏览器标签页，看了 3 篇对比文章，2 小时后——**什么都没决定**。

**停。** 纠结是因为信息不足，而 Agent 能在 10 分钟内给你一个「能跑的原型」，让事实说话。

---

## 🎯 技巧一：让 Agent 当「快速验证机」

核心心法：**先让 Agent 搭一个能跑的最小版本，跑起来再看，别在脑子里推演。**

### 实操流程

**Step 1：描述你的纠结**

```
我在纠结两个方案：

方案 A：用 SSE（Server-Sent Events）做服务端推送
方案 B：用 WebSocket 做双向实时通信

我的场景是：一个在线协作编辑器，需要实时同步光标位置和文本变更。

请帮我：
1. 分别用两个方案搭一个「最小可运行原型」（MVP）
2. 每个原型控制在 50 行核心逻辑以内
3. 跑起来后告诉我各自的延迟、代码复杂度、扩展性对比
```

**Step 2：看 Agent 跑出来的结果**

Agent 会给你两个能直接运行的代码片段，你可能会看到：

> **SSE 原型**：20 行后端 + 15 行前端，浏览器原生支持，自动重连，但只能服务端→客户端单向。
>
> **WebSocket 原型**：30 行后端 + 25 行前端，需要额外库，支持双向，但要自己处理心跳和重连。

**Step 3：基于事实做决策**

不再是"我觉得"，而是：
- "SSE 原型的代码量少 40%，而且我的场景目前确实只需要服务端推送"
- "但 WebSocket 的原型也跑通了，如果 2 周后要做光标实时协作，迁移成本不高"

**10 分钟前你在纠结，10 分钟后你有两个能跑的原型。**

## 🔪 技巧二：「验证完就扔」的心态

Spike 的核心不是产出代码，是**买信息**。

### 什么值得 Spike？

| 场景 | 例子 | Spike 目标 |
|---|---|---|
| 技术选型 | Redis vs RabbitMQ 做任务队列 | 哪个延迟更低、代码更简洁 |
| 可行性验证 | "能不能用 AI 自动生成 API 文档" | 跑通一条从代码到文档的流水线 |
| 第三方库评估 | 换个新的图表库 | 同样数据渲染出来，哪个更顺滑 |
| 架构方向 | 微服务拆分还是单体 + 模块 | 拆分后的通信成本到底多高 |

### 什么不值得 Spike？

- 已经有明确答案的问题（"HTTP 还是 HTTPS"——别 Spike 了）
- 需要大量数据才能验证的（"这个算法在 100w 用户下表现如何"——先上线再 A/B 测）
- 纯主观偏好的（"这个颜色好看还是那个好看"——问设计师）

### 「用完即弃」原则

```
注意：这只是 Spike 原型，验证完思路就删。
不要写测试、不要考虑边界 case、不要优化性能。
能跑起来证明思路可行就行。
```

**对 Agent 明确说「这是 Spike」，它就不会过度工程化。**

## 🛠️ 各工具实操

### Claude Code

```
我想验证一个技术方案是否可行：用 FFmpeg wasm 在浏览器端做视频压缩。

请帮我：
1. 搭一个最小 HTML 页面，加载 FFmpeg wasm
2. 实现「选择一个视频文件 → 压缩到 720p → 下载」
3. 代码越简单越好，不要错误处理，不要 UI 美化
4. 跑通后告诉我：压缩 10MB 视频大概要多久、内存占用多少

这是 Spike，验证完就删，不用写测试。
```

Claude Code 会直接把文件写到磁盘，你打开浏览器就能跑。

### Cursor

Cursor 的 **Composer** 特别适合 Spike：

1. 在 Composer 里输入上述 prompt
2. 让 Cursor 生成完整代码
3. 直接运行，看结果
4. **不保存文件**——关窗口即走

### Kimi Code

Kimi Code 的长上下文优势：**一次性把多个方案都 Spike 了**。

```
我想对比三个状态管理方案：Zustand、Jotai、Redux Toolkit。

请分别用三个方案实现同一个功能：
- 一个计数器 + 一个异步获取用户列表
- 每个方案控制在 30 行以内
- 告诉我：代码量、心智负担、TypeScript 支持度对比

这只是对比 Spike，不需要完整项目结构。
```

## 🧠 为什么这招有效？

| 没有 Spike | 有 Spike |
|---|---|
| 2 小时看文档、纠结、开会议 | 10 分钟跑原型，用事实说话 |
| 决策基于「我觉得」「某大牛说」 | 决策基于「我跑过，A 方案延迟 50ms，B 方案 200ms」 |
| 怕选错，所以迟迟不动 | 验证成本低，错了就换，不心疼 |
| 过度设计（"万一以后要……"） | 只解决当下问题，未来需要时再 Spike |

**核心原因**：人类的想象力在「预测未来」这件事上准确率很低，但 Agent 搭原型的成本极低。**与其猜，不如跑。**

## 💡 进阶玩法

### 玩法 1：让 Agent 写「对比报告」

```
基于刚才两个原型，帮我写一份「Spike 对比报告」，包含：
1. 代码复杂度评分（1-5 星）
2. 运行时性能对比
3. 维护成本预估
4. 你的推荐方案 + 理由

格式要简洁，方便我转发给团队看。
```

### 玩法 2：「预演失败」

```
假设我们选了方案 A，3 个月后可能会遇到什么坑？
列出 3 个最可能的问题，以及每个问题的预警信号。
```

Agent 会基于原型的局限性，帮你预判风险。

### 玩法 3：建立「Spike 仓库」

把验证过的原型存到一个单独的 `spikes/` 目录：

```
spikes/
├── 2026-09-08-websocket-vs-sse/
├── 2026-09-05-redis-vs-rabbitmq/
└── 2026-08-28-ffmpeg-wasm/
```

**不是留给生产用，是留给未来的自己做参考。** 半年后遇到类似问题，直接看当时的 Spike，省去重新纠结。

## 📝 今天记住这个

| 场景 | 操作 |
|---|---|
| 纠结两个技术方案 | 让 Agent 各搭一个 50 行原型，跑起来对比 |
| 想试新技术但怕踩坑 | 明确说「这是 Spike，验证完就删」，降低心理门槛 |
| 团队争论不休 | 把争论变成「各自 Spike，20 分钟后看原型」 |
| 怕过度设计 | 只 Spike 当下需要的能力，不要「万一以后」 |
| Spike 完想留档 | 扔到一个 `spikes/` 目录，写 3 行 README 说明结论 |

> **核心心法**：纠结是最贵的成本。Agent 把「验证一个想法」的成本从 2 小时降到 10 分钟，那你应该验证 10 个想法，而不是纠结 1 个。
>
> 记住：Spike 不是偷懒，是**用最低成本买最多信息**。原型跑起来的那一刻，纠结就结束了。🔪
