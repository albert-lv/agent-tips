# 09-30 — 停机权交给谁：让 Agent 自己知道「什么时候该停」

## 🤔 你有没有干过这种 babysitting

给 Claude Code 派了个活，然后你就变成了它的监工：

- 隔两分钟瞟一眼终端，看它是不是跑偏了
- 它干完了你不放心，又自己跑一遍测试确认
- 或者更惨——你没看，它 loop 了 40 轮还在「继续优化」，token 账单比你的午饭贵

问题的根源都一样：**停机权在你手里，但你不想一直握着。**

今天的主题就一件事：把「什么时候停」这件事，交给一个更靠谱的裁判。

## 🛠️ 技巧一：`/goal` —— 给 Agent 一个「通关条件」，而不是一个「任务」

普通派活是这样的：

```text
把这三个模块迁移到新的日志库
```

它干完了吗？不知道。干得好吗？不知道。你只能盯着。

**Claude Code 的 `/goal` 玩法是倒过来的**：你先告诉它「什么算赢」，它自己朝着那个状态走，走到就停。

```text
/goal 跑通 dotnet test 全绿，且 src/ 下不再有任何
引用旧日志库的 using 语句
```

区别在哪？**「迁移三个模块」是过程，「测试全绿 + 零旧引用」是状态。** 过程需要人盯，状态可以机器验。

而且 `/goal` 的妙处是：它不是你催它它就停，而是一个**独立的 evaluator 模型在每个回合结束后复核**「赢的条件成立了吗」。成立了 → 停机；没成立 → 继续干。你大可以端杯咖啡去开别的会。

> 💡 为什么独立复核很重要：干活的手和验收的手不是同一只，这是 09-24「交叉评审」的同款逻辑。让运动员自己吹终场哨，你放心吗？

## 🛠️ 技巧二：自治工具有六种，拿 workflow 改 6 个文件是「用大炮打蚊子」

这是今天最想让你记住的一张表。六种「让 Agent 自己跑」的工具，**差别只有两件事：谁拿着计划？什么决定停机？**

| 工具 | 谁拿计划 | 什么时候停 | 什么时候用 |
|---|---|---|---|
| 普通 prompt | Claude，单回合内 | 它自己判断干完了 | 检查便宜、你在旁边看着 |
| `/goal` | Claude，逐回合 | 独立模型确认条件达成 | 有一个**可验证的终态**（比如 build 绿） |
| `Stop` hook | 你的脚本 | 你的脚本跑完退出码为 0 | 团队里**所有人、每个会话**都不能跳过的闸 |
| `/loop` | Claude，按次运行 | 你手动停 | 轮询外部状态，比如盯 CI |
| Workflow / `/batch` | 一段脚本 | 脚本执行完 | 几百个文件的大迁移 |
| Agent teams | 一个 lead agent | 任务清单清空 | 多条长线工作流要协调 |

三条速记：

1. **一个 feature → `/goal`**；**一个大迁移 → workflow**；**一条团队红线 → Stop hook**。其他都是这三种的变体。
2. Workflow 有 16 并发、单跑 1000 个 agent 的上限——**但真正的上限是你的钱包**：同一批活，workflow 烧的 token 可能是对话模式的十倍。先拿一个目录试跑，再全量开。
3. **「拿 workflow 改 6 个文件」是最典型的贵工具办便宜事。** 如果你能用一句话描述那个 diff，普通 prompt 就够了。

> 💡 反过来的错误也存在：几百个文件的机械迁移，硬塞进一个交互会话里让它逐文件处理——上下文会被中间结果撑爆。脚本持有循环、分支和中间结果，你的上下文只看到最终答案，这才是 workflow 的设计初衷。

## 📝 今天记住这个

| 场景 | 姿势 |
|---|---|
| 有一个能跑命令验证的终态（build 绿 / 测试过） | 写成 `/goal` 条件，别当人肉监工 |
| 团队红线（如「不过测试不许提交」） | 写 `Stop` hook，脚本把关 |
| 几百个文件的机械迁移 | 上 workflow，先小目录试跑 |
| 就改几个文件 | 普通 prompt，别想太多 |

**一句话总结：停机权，能给机器验证的，就别留在自己手里。** 你的注意力比 token 贵多了。
