# 09-29 — 纠错的两笔账：改写花一次钱，叠写每轮都收税

## 🤔 一个没人算过的账

同一个错误，有人花 500 token 解决，有人花 5000。差别不在 prompt 写得好不好，在**纠错姿势**。

看你有没有干过这种事：

- Claude 理解歪了，你追发一句"不对，我的意思是……"——然后这条误解对话**永远留在上下文里**，之后每一轮都被重新读一遍
- 它生成的 2000 字里只有一段不对，你懒得指，直接"重新生成一遍"——等于花 2000 个输出 token 修一段落
- 同一个规范被它 violate 了三次，你纠正了三次——下个月它接着犯

今天这两个技巧，就是把这三笔冤枉钱一笔笔省下来。

## 🛠️ 技巧一：改消息，而不是叠消息

**Claude Code** 里，发现上一条消息说错了、或被理解歪了，**按 `↑` 直接编辑那条历史消息**，改完重新发送。

对比一下这笔账：

| 姿势 | 上下文里留下什么 |
|---|---|
| 叠消息（追发纠正） | 错误的原话 + 它的错误回答 + 你的纠正，三段全留着，之后每轮复读 |
| 改消息（编辑替换） | 只有修正后的版本，误解对话直接蒸发 |

省的不只是那一两条消息本身——**驻留垃圾的可怕之处在于复利**：上下文每多 1000 token，之后每一轮请求都在为它多付费。一个被误解的回合，可能陪着你们直到会话结束。

Cursor / Windsurf 同理：对自己刚发的 prompt 点编辑（Cursor 在消息气泡旁有 edit 按钮），替换而不是追加。

> 💡 例外：如果它的错误回答恰好暴露了有用的探索过程（比如"虽然理解歪了但歪打正着发现了那个 bug"），那就别编辑，留着。改消息的目的是清垃圾，不是搞记忆抹除。

## 🛠️ 技巧二：只改错的段落，别全文重生成

这个最反直觉：**"重新生成一遍"是纠错里第二贵的操作**（最贵的是推倒重来，09-28 讲过怎么避免）。

它吐了 2000 字，第三段里的 SQL 有个错。正确姿势是**指认位置 + 限定范围**：

```text
第三段那个 JOIN 的条件写反了，
user_id 应该关联 orders.user_id 而不是 orders.id。
其他段落一个字都别动。
```

`"其他别动"` 这四个字价值千金——没有它，模型默认会全文重吐一遍，你花 2000 output token 买了 1950 个本来就已经正确的字。

**进阶：纠错的尽头是「不再纠错」。** 如果你发现自己在第三次纠正同一个问题，停手——把这条规则写进项目的 `CLAUDE.md`：

```markdown
## 数据库规范
- JOIN 条件必须显式写两边表名，禁止裸写列名
```

写一次，之后每个新会话启动自动加载。这就是 09-25 说的"自定义外挂"的思路，只不过这个外挂的原料是你的耐心。

> 💡 窄范围纠错的隐藏收益：它逼你说清"到底哪里错了"。很多"AI 理解能力差"的抱怨，追到最后其实是自己没定位到具体位置，只能含糊地说"感觉不对"。

## 📝 今天记住这个

| 场景 | 姿势 |
|---|---|
| 上条消息说错 / 被理解歪 | `↑` 编辑原消息替换掉，别让误解对话驻留 |
| 长输出只有一小段错 | 指认具体段落 + "其他别动"，拒绝全文重生成 |
| 同一个错纠了三遍 | 写进 `CLAUDE.md`，一劳永逸 |

一句话总结：**纠错不是按字数计费，是按"复读次数"计费——改写花一次钱，叠写每轮对话都收税。** 💸
