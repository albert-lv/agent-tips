# 09-04 — Agent 的「diff 聊天术」—— 看代码别干瞪眼，和 AI 聊出来

> **一句话：面对几百行的 diff，别自己硬啃，让 Agent 陪你聊，3 分钟抓住重点。**

---

## 😵 这个场景是不是很熟悉

你打开一个 PR，diff 整整 400 行，改了 8 个文件。 commit message 就写了个 "fix bug"。

你盯着屏幕，心里只有一个问题：

> **"这到底改了啥？我为啥要看这些？"**

硬看？20 分钟过去，你只知道自己越来越困。

**让 Agent 来当 diff 搭子？** 3 分钟聊清楚改动了什么、动机是啥、哪里有坑。

---

## 🗣️ 技巧一：先让 Agent 「一句话翻译」

把 diff 丢给 Claude Code（或者直接粘贴到 Cursor / Kimi Code）：

```
这是这次改动的 diff，用 2-3 句话告诉我：
1. 核心改动了什么
2. 为什么要这么改
3. 哪个文件是主战场
```

Agent 会给你一个 **人话版本** 的总结：

> "这次主要是在 `PaymentService` 里加了一个重试机制（之前是直接抛异常），因为第三方支付接口经常超时。主战场是 `src/services/payment.ts`，其他文件都是跟着改的类型定义。"

**这就是你的导航地图。** 你再看 diff 的时候，知道哪块是主角、哪块是龙套。

---

## 🔍 技巧二：递进式追问——从「改了什么」到「会炸哪里」

别停在一句话总结，继续聊：

**Round 2 — 影响面：**
```
基于这个改动，哪些模块可能受到影响？
列出 3 个最值得关注的连锁反应。
```

**Round 3 — 风险点：**
```
如果我是 reviewer，这次改动我最应该盯着看什么？
有哪些地方容易埋雷？
```

**Round 4 — 测试建议：**
```
如果要验证这次改动没翻车，最少需要测哪几个场景？
```

你会发现，Agent 给的风险点往往是你自己看 diff 会漏掉的——因为它会基于全局代码库做联想，而你盯着 diff 的时候很容易「见树不见林」。

---

## 🎯 技巧三：让 Agent 当「反向辩护人」

这招更进阶——让 Agent 故意挑刺：

```
假设你是一个严格的 code reviewer，找出这次改动里
你最不满意的 3 个点，以及具体改进建议。
```

Agent 会进入「挑刺模式」，给你列出：

| 挑刺点 | 具体位置 | 改进建议 |
|---|---|---|
| 重试次数硬编码为 3 | `payment.ts:42` | 抽到配置文件里，方便线上调整 |
| 没有记录重试日志 | `payment.ts:45-50` | 每次重试记一条 warn，方便排查 |
| 异常类型判断太宽泛 | `payment.ts:38` | 区分网络超时和业务异常，不该重试的别重试 |

**这些点不一定是真正的 blocker，但给你一个「别人会怎么看这段代码」的视角。** 比你自己脑补 reviewer 的心理活动准多了。

---

## 🛠️ 跨工具速查

| 你想做什么 | Claude Code | Cursor | Kimi Code |
|---|---|---|---|
| 贴 diff 总结 | 直接粘贴 + 提问 | Chat 里贴 diff | 粘贴到对话 |
| 基于仓库上下文分析 | 天然支持（在仓库目录运行） | 打开项目后分析 | 打开项目后分析 |
| 让 AI 模拟 reviewer | `@` 引用文件后提问 | 选中代码 + Chat | `#文件` 引用后提问 |

---

## 📋 今天记住这个

| 场景 | 做法 |
|---|---|
| 面对大 diff，不知道从哪看起 | 先丢给 Agent，要 **一句话翻译** |
| 想知道改动有什么连锁反应 | 追问 **影响面 + 风险点** |
| 想提前预判 reviewer 会说什么 | 让 Agent 进入 **反向挑刺模式** |
| 快速判断要不要 approve | 问 Agent **最少需要测哪几个场景** |

---

> 💡 **核心心法**：diff 不是用眼睛「看」的，是用来「聊」的。Agent 的优势不是读得快，而是能把改动翻译成「为什么」，还能站在全局挑毛病。**你自己看 diff 是阅读，和 Agent 聊 diff 是对话——后者信息量大多了。**
>
> 下次再看到 "fix bug" 的 commit message，别叹气，把 diff 甩给 Agent，3 分钟后你就是最懂这段代码的人。🎯
