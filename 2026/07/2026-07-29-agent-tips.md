# 🤖 Agent 技巧日签 · 2026-07-29

## 今日主题：让 Agent 自己「找茬」——写完先审一遍的隐藏收益

你有没有发现，Agent 写代码的时候特别自信？

改完 20 个文件，跟你说「搞定」，结果你一扫——命名 inconsistent、边界情况没处理、甚至还有个变量名拼错了。🫠

不是它不会审，是你没让它审。**Agent 其实挺会找自己茬的，前提是你要它找。**

---

## 💡 技巧一：Claude Code 的「先别动，让我想想」模式

Claude Code 默认是「边说边做」——你提需求，它直接改文件。但你可以让它先**出方案、不执行**，等你确认再动手。

### 用法：加一句「先别改，给我看看计划」

```
我想给登录接口加个 rate limit。

先别改文件，给我一份执行计划，包括：
1. 要改哪些文件
2. 每处改动的理由
3. 潜在的 side effects
4. 有没有更简单的替代方案

我确认后再动手。
```

Claude 会输出一份「施工图纸」，你扫一眼发现：
- "哦原来 `auth.ts` 和 `middleware.ts` 都要动"
- "等等，它想在数据库层加计数器，但我想要内存版的"
- "这个 side effect 我没考虑到——会影响 existing sessions"

**你花 30 秒看计划，省掉 30 分钟回退。**

### 进阶：让它自己给自己挑刺

```
基于上面的计划，请以"代码审查员"的身份挑三个问题：
- 这个方案里最脆弱的一环是什么？
- 如果并发量突增，哪里会先崩？
- 有没有遗漏的测试场景？
```

Claude 会进入「自我怀疑」模式，往往能发现自己方案里的漏洞。这时候你还没花一分钱 token 在改文件上。

> 💡 **小总结**：Claude Code 的 `APPLY` 按钮是最后的防线——在它出现之前，你有无数次机会说「再想想」。

## 💡 技巧二：Cursor 的「Review 后再 Apply」——Composer 的安全带

Cursor 的 Composer Agent 有一个很多人跳过的步骤：**Agent 改完后，先 review 再 apply。**

### 默认流程 vs 安全流程

| 模式 | 发生什么 |
|------|---------|
| 默认（Accept All）| Agent 改完，一键全收，直接写盘 |
| 安全（Review First）| Agent 改完，以 diff 形式呈现，你逐条审 |

### 怎么用

在 Cursor 设置里：
```
Settings → Features → Composer → Auto-apply edits → OFF
```

关掉自动应用后，Composer 每次改完都会把改动列成清单：
- `src/auth.ts` → 改了函数签名
- `src/middleware.ts` → 新增 rate limit 逻辑
- `tests/auth.test.ts` → 新增 3 个测试

你可以**逐文件勾选**哪些要、哪些不要。看到 `package.json` 也被改了？取消勾选，问它「你动我依赖干嘛？」

> 💡 **小总结**：Cursor 的 diff review 不是拖慢你，是让你从「改完再修」变成「审完再收」。后者省时间得多。

## 🧊 今日冷知识

Kimi Code 其实也有类似的「暂停」能力——在设置里打开 **「AI 修改需确认」** 后，Kimi 不会直接写文件，而是把改动以「建议」形式贴在编辑器侧边栏，你可以像处理 GitHub Suggestion 一样逐条采纳或忽略。

适合那种"让它随便看看，但我有最终拍板权"的场景。

## 一句话总结

> Agent 的自信是它的优点，也是它的盲区。**让它先出计划、再自我审查、最后等你拍板**——三步下来，翻车率能降一半。

毕竟，修 bug 的 token 比审方案的 token 贵多了。💸
